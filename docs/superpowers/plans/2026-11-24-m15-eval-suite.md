# M15 — Eval Suite: Design and Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Owner-built milestone.** Part 1 explains the design and the reasoning behind each decision,
> so it can be changed deliberately. Part 2 is the task plan. Start after M12 (agent corrections)
> merges, because approved corrections are the best source of eval cases.

**Goal:** Let an admin measure whether a bot answers correctly, from the right sources, before and
after changing its prompt, model, threshold or knowledge, and optionally block publishing a prompt
that scores worse.

**Architecture:** Per-bot datasets of cases (question → expectations) are run as background jobs.
Each case goes through the real chat pipeline in a new orchestrator mode, `eval`. That mode is the
playground path plus overrides; nothing is persisted as a conversation. Retrieval metrics are
computed from the trace's `retrieval` column. Answer quality is graded by a configurable
LLM-as-judge through the existing `Llm` service. Results are stored per case, aggregated per run,
and compared run-to-run in the admin.

**Tech Stack:** NestJS, pg-boss, Postgres, Vercel AI SDK (behind `Llm`), Zod, React admin.

**Spec:** `docs/spec.md` §27 Phase 3: "Eval suite: per-bot datasets of question → expected answer
/ expected sources; graded by retrieval metrics plus LLM-as-judge; run on demand and before
publishing a prompt", and "Prompt versioning UI: diff two versions, run the eval dataset against a
draft, publish, roll back."

## Global Constraints

See `2026-11-24-00-phase2-index.md`. Also:

- **No LLM in CI.** Integration tests use the `mock` provider with scripted judge replies. The live judge is only exercised manually or in `live-providers.yml`.
- **Costs count.** Eval runs are costed and count toward the bot's monthly spend cap. A run stops when the cap is reached, and is never silently free.
- **Untrusted text.** Judge prompts treat case text and answers as untrusted data inside delimiters, the same rule as agent assist (`escapeAgentAssistText`).

# Part 1 — Design

## 1. Concepts

| Concept      | What it is                                                                                                                                                                                                                    |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dataset**  | A named, per-bot list of cases. A bot may have several (e.g. "Refund FAQ", "Out-of-scope", "Regression"). Datasets are versioned by `updated_at`, and each run snapshots its cases, so later edits don't change past results. |
| **Case**     | One question plus expectations. Expectations are optional, and each one present adds a metric. Cases can have short prior turns (history).                                                                                    |
| **Run**      | One execution of a dataset against one configuration: prompt version, chat model, retrieval threshold, and judge model. Runs are immutable once finished.                                                                     |
| **Result**   | The per-case outcome of a run: retrieved chunks, answer text, decision (answered/escalated), metric values, judge verdict and rationale, tokens and cost.                                                                     |
| **Baseline** | The run a new run is compared to: by default the latest finished run of the same dataset on the bot's _active_ configuration.                                                                                                 |

## 2. Case expectations and metrics

Each expectation is independent. A case with only `expectedDocumentIds` is a pure retrieval test.
A case with `expectHandoff: true` tests escalation.

| Expectation field     | Type                          | Metric(s) it enables                                                                                                                                                                                                                                                   |
| --------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `expectedDocumentIds` | `string[]` (1–10)             | **hit@k**: any expected doc among the top-k _used_ chunks (k = chunks used in the prompt, max 5). **MRR**: 1/rank of the first expected doc in the retrieved top 8, else 0. **Citation accuracy**: share of the answer's citations that point to an expected document. |
| `expectedAnswer`      | `string` (≤ 4,000)            | **Judge correctness** (`correct` / `partially_correct` / `incorrect`) and **judge score** 0–1.                                                                                                                                                                         |
| `mustInclude`         | `string[]` (≤ 10, each ≤ 200) | **Must-include pass**: every phrase appears, case-insensitive with whitespace normalised (deterministic; catches prices, durations, names).                                                                                                                            |
| `mustNotInclude`      | `string[]` (≤ 10)             | **Must-not-include pass** (deterministic; catches competitor names, banned promises).                                                                                                                                                                                  |
| `expectHandoff`       | `boolean`                     | **Escalation accuracy**: the pipeline escalated (or offered handoff) if and only if this is `true`. Out-of-scope cases use `true`.                                                                                                                                     |

A run also records, per case, `latencyMs`, `ttftMs`, `inputTokens`, `outputTokens` and
`costUsd` from the trace.

**Run aggregates:** the mean of each metric over the cases that have the expectation, plus counts,
total cost, p50/p95 latency, and a **pass rate**. A case _passes_ when every metric it has passes:
hit@k = 1, judge = `correct` (or `partially_correct` when the dataset allows partial),
must-include and must-not-include pass, and escalation is accurate.

Why both deterministic checks and a judge: the judge catches paraphrased wrong answers, while
`mustInclude` catches the "14 days vs 30 days" errors a lenient judge misses. Deterministic metrics
are also free and stable across judge-model changes.

## 3. The judge

- **Configuration:** the judge credential and model are chosen per run (defaulting to a workspace setting). They may differ from the bot's model; using a stronger judge than the answering model is recommended and stated in the UI.
- **Settings:** temperature 0, `maxOutputTokens` 300, and the prompt is versioned (`eval-judge-v1`) and stored on the run, so a judge-prompt change is visible in comparisons.
- **Input:** the question, the expected answer, the bot's answer, and the cited source excerpts (the used chunks, trimmed to 6,000 characters total). All of it is escaped and delimited.
- **Output:** strict JSON `{ "verdict": "correct" | "partially_correct" | "incorrect", "score": number (0–1), "rationale": string (≤ 400 chars), "unsupportedClaims": string[] (≤ 5) }`. It is parsed with `parseModelJson` (fenced output is normal) and validated with Zod. A parse failure retries once with the same input, then records `judge_error` for that case without failing the run.
- **Rubric** (in the prompt): `correct` = it states the facts in the expected answer without contradicting them and adds no unsupported material claims; `partially_correct` = it is missing a material fact but contradicts none; `incorrect` = it contradicts the expected answer, makes unsupported material claims, or answers a question it should have handed off.
- **Calibration:** ship 20 hand-labelled judge fixtures (`apps/api/test/eval/judge-fixtures.json`). The live-provider workflow reports judge agreement with the labels, and the docs state the agreement observed.

## 4. Running a case through the real pipeline

- **New orchestrator mode:** `{ kind: 'eval'; runId: string; caseId: string; history: { role: 'visitor' | 'ai'; content: string }[]; content: string; overrides: { promptVersionId?: string; chatCredentialId?: string; chatModel?: string; retrievalThreshold?: number } }`.
- **Reuse:** it reuses everything the playground mode does: no conversation rows, a trace written with `origin = 'eval'`, and no realtime or integration events.
- **Overrides** are applied only in this mode, and only after validation (the prompt version belongs to the bot; the credential belongs to the workspace and serves chat).
- **Sink:** a `CollectingAnswerSink` implements `AnswerSink` and records deltas, the final content, citations and the escalation event in memory.
- **Shared caps:** handoff intent, escalation, link policy, citation parsing and spend caps all run unchanged. Evals measure the product, not a copy of it.

## 5. Execution model

- **Jobs:** `eval.run` (one per run) fans out `eval.case` jobs (one per case), with concurrency 4 per run and 1 run per bot at a time.
- **Progress:** the run status goes `queued → running → completed | failed | cancelled`. Progress (`casesDone / casesTotal`) is published with `notifyWorkspace({ type: 'eval.updated', runId })`.
- **Limits:** 500 cases per dataset and 3 concurrent runs per workspace. A run stops with `failed: spend_cap_reached` when the bot's cap is hit, and completed results are kept.
- **Cancel** marks the run `cancelled`. In-flight cases finish; queued ones are skipped.

## 6. Publishing gate (prompt versions)

- **Draft runs:** the Prompts tab can run any dataset against a _draft_ prompt version (saved but not activated), then compare it with the baseline.
- **Gate setting:** optional per-bot setting `evalGate = { datasetId, minPassRate, maxRegression }`. When it is set, activating a prompt version requires a completed run of that dataset on that version from the last 7 days, with `passRate >= minPassRate` and `baseline.passRate - passRate <= maxRegression`. Otherwise activation returns `conflict` with the numbers.
- **Override:** owners can override the gate with a typed reason, which is audited.

## 7. Where cases come from

1. **Manual:** add cases in the admin.
2. **Approved corrections (M12):** an approved suggestion offers "Add to dataset", turning `question` → case and `answer` → `expectedAnswer`, with `expectedDocumentIds` set to the created source's document.
3. **Thumbs-down answers:** from the usage page's negative-feedback report, "Add to dataset" turns the question → case with no expectation yet, flagged `needsExpectation`.
4. **Import:** JSON in the same shape as `apps/api/test/rag/fixtures/questions.json` (`inScope` with `q` / `expectedDoc`, `outOfScope`), mapping document titles to ids. This also covers the agent-assist evaluation fixtures.
5. **Export:** a dataset exports to versioned JSON (`{ "format": "ailoom-eval-dataset", "version": 1, "cases": [...] }`), which feeds the Phase 4 config export.

## 8. Data model

| Table           | Columns                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `eval_datasets` | `id`, `workspace_id`, `bot_id` (FK bots ON DELETE CASCADE), `name` (≤ 100, unique per bot), `description`, `allow_partial boolean DEFAULT false`, `created_by`, `created_at`, `updated_at`                                                                                                                                                                                                                                                                                                                                  |
| `eval_cases`    | `id`, `workspace_id`, `dataset_id` (FK CASCADE), `question` (≤ 2,000), `history jsonb DEFAULT '[]'`, `expected_answer`, `expected_document_ids uuid[] DEFAULT '{}'`, `must_include text[]`, `must_not_include text[]`, `expect_handoff boolean NULL`, `needs_expectation boolean DEFAULT false`, `origin` (`manual`/`correction`/`feedback`/`import`), `origin_ref uuid NULL`, `created_at`, `updated_at`                                                                                                                   |
| `eval_runs`     | `id`, `workspace_id`, `bot_id`, `dataset_id`, `status eval_run_status`, `config jsonb` (prompt version id, chat provider/model, threshold, judge provider/model, judge prompt version), `cases_snapshot jsonb`, `cases_total`, `cases_done`, `summary jsonb NULL`, `baseline_run_id NULL`, `cost_usd numeric(12,6) DEFAULT 0`, `error text NULL`, `created_by`, `created_at`, `started_at`, `finished_at`                                                                                                                   |
| `eval_results`  | `id`, `workspace_id`, `run_id` (FK CASCADE), `case_id` (nullable: the case may be deleted later; the snapshot keeps the text), `trace_id` (FK generation_traces SET NULL), `decision`, `answer text`, `citations jsonb`, `retrieved jsonb`, `metrics jsonb` (`{ hitAtK, mrr, citationAccuracy, mustInclude, mustNotInclude, escalationCorrect, judge: { verdict, score, rationale, unsupportedClaims } \| null }`), `passed boolean`, `error text NULL`, `latency_ms`, `cost_usd`, `created_at`; unique `(run_id, case_id)` |

Enum changes: `trace_origin` gains `'eval'`; a new `eval_run_status` enum is
`queued | running | completed | failed | cancelled`.

Retention: runs older than 180 days are deleted, except each dataset's latest completed run and
any run referenced as a gate's evidence.

## 10. Admin UI

- **Evaluate tab** on the bot, with three sections:
  - Datasets (list and case editor)
  - Runs (list with pass rate, cost, and a delta against the baseline)
  - Run detail: metric cards with deltas; a results table filterable to failed or regressed; and a case drawer showing question, expected answer, actual answer, citations, judge rationale, and a link to the trace replay
- **Prompts tab:** "Evaluate this version" on drafts, and the gate status on Activate.
- **Corrections queue and negative-feedback report:** "Add to dataset".

## 11. Explicitly out of scope for M15

- Fine-tuning or automatic prompt optimisation.
- Pairwise A/B judging.
- Multi-turn simulations beyond the stored `history`.
- Embedding-model comparison runs. These need a re-embed per run; a follow-up can run against a shadow index.

# Part 2 — Implementation plan

## Review Focus

1. A case's expected document is deleted after the case was written: hit@k is computed against the snapshot ids, the case is flagged `stale_expectation` in results, and it is excluded from hit@k aggregates instead of counting as a miss. Test it in Task 3.
2. The judge returns fenced or invalid JSON: one retry, then `judge_error` on that case only, and the run still completes. Test it in Task 4.
3. The spend cap is hit mid-run: the run stops as `failed: spend_cap_reached`, finished results remain, and the cost totals match the traces. Test it in Task 3.
4. The bot is deleted during a run: the remaining cases are skipped, the run is `failed: bot_unavailable`, and no orphan jobs remain. Test it in Task 3.
5. A dataset is edited while a run is in flight: the run uses `cases_snapshot`, so the results reference the snapshot text. Test it in Task 3.
